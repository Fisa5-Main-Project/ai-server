# 보수적인 금융상품 추천

2026-11-02 구현. 실제 운영 성과를 측정한 문서가 아니다.

## 처리 흐름

MySQL의 현재 구조화 프로필 → 요청 해석 → 상품 메타데이터 검색 → 코드 적합성 검증 → 정형 응답 → MongoDB 감사 기록 → API/SSE 반환.

LLM은 상품군·금융사를 해석하며 고객 성향, 자산, 위험등급을 정하지 않는다. 명시한 상품군·금융사·제외 조건·금액·기간은 코드로 제한한다. 일반 추천은 예금/적금으로 시작한다. 검색 후보는 상품군별 최대 20개, 반환은 낮은 위험을 우선하여 최대 3개다. 각 상품은 대안이며 동시에 가입할 자산배분안이 아니다.

## 차단 정책

- 내부 정규화 위험 척도: 1이 가장 위험, 6이 가장 낮음. 1~3등급은 모든 고객에게 차단.
- 원금보장형/안정형: 6등급과 명시적 원금보장 확인 필요. 안정추구형: 5~6등급. 위험중립형·적극투자형·공격투자형: 4~6등급. 법적 적합성 판정표가 아닌 이 서비스의 보수적 정책이다.
- 성향 미등록, 입출금 자산 누락·잘못된 금액·잔액 부족, 최소 가입금액 미확인 시 제외. 총자산이나 부동산을 즉시 투자 가능한 자금으로 간주하지 않는다.
- 과거 싫어요가 한 번이라도 있으면 제외. 좋아요는 적합성을 통과한 동일 위험등급 후보의 우선순위에만 사용.
- 위험등급 누락, 근거 미확인, 확인일이 미래이거나 30일 초과, 판매 유효기간 만료, 일반 개인 가입 여부 미확인, 별도 가입자격 제한이 있는 상품은 제외.
- KVIC 벤처조합 자료는 개인 가입용 상품으로 취급하지 않는다.
- 요청한 금융사가 검색되지 않아도 다른 금융사의 상품으로 대체하지 않는다. 제외한 금융사·상품군, 예산 초과, 요청 기간 초과 또는 기간 미확인 후보도 제외한다.
- 고객 정보·피드백·검색·감사 기록 장애 시 추천을 보류한다. 강제 추천/빈 배열 금지 규칙은 제거했다.

## 데이터 준비 — 배포 전에 필요

추가 구현: [상품 근거 보강과 내부 위험분류](product-evidence.md). 상품 자체에 위험등급이 없는 경우 공식 등급을 만들지 않고, 공식 자료에서 확인한 특성으로 내부 분류를 계산한다. 현재 예금 3종의 근거를 포함하며, 아래 JSON은 기존 수동 v1 형식이다. 새 v2 형식은 `server/app/rag/data/product_evidence.json`과 위 문서를 따른다.

기존 수집 데이터는 위험등급과 가입 가능 여부를 충분히 제공하지 않는다. 따라서 기존 문서를 자동으로 안전하다고 간주하지 않는다. **아래 검증 정보를 보강하기 전에는 추천이 비어 있을 수 있다.** 실제 상품설명서/판매사 자료를 검토한 관리자가 통합 컬렉션의 해당 상품에 `suitability` 객체를 추가해야 한다. 임의의 기본값으로 전체 상품을 승인하지 않는다.

대상: `products_deposit_saving`, `products_annuity`, `products_funds`.

```json
{
  "suitability": {
    "risk_grade": 6,
    "principal_guaranteed": true,
    "min_amount": 10000,
    "term_months": 12,
    "retail_available": true,
    "eligibility_unrestricted": true,
    "verified_on": "2026-11-02",
    "valid_until": "2026-11-30",
    "evidence_source": "실제 확인한 판매사 문서의 URL 또는 문서 식별자",
    "company_name": "확인한 판매사명"
  }
}
```

이 예시는 실제 상품의 검증 결과가 아니다. 원본 문서에 금액/기간 옵션이 여럿이면 하나의 확인된 가입 옵션을 나타내도록 기록한다. `min_amount`는 해당 옵션의 필요 가입금액이며 수익률이 아니다. 상품 내용이 변경되면 재검증한다. 조건부 가입 상품은 자동 적합성 판정 대상에서 제외한다. 원금보장과 예금자보호는 같은 의미로 해석하지 않는다.

현재 회사명은 명시된 문자열/일부 별칭으로 검사한다. 복잡한 복합금액, 임의의 자연어 조건, 장기 현금흐름·세제 적합성을 모두 판정하는 기능은 아니다. 검증 불가 상품을 안전한 것으로 추론하지 않으며, 가입 전 판매사에서 최종 조건을 확인해야 한다.

## API와 챗봇

기존 `products` 및 legacy 필드는 유지한다. `request_id`, `status`, `message`를 추가했다. 상태는 `ok`, `no_suitable_products`, `unavailable`이다.

추천 챗봇의 자유 생성 답변은 검증된 상품의 정형 설명으로 바꿨다. 일반 개념 설명은 검토된 설명문을 사용한다. 개인별 자산배분을 자유롭게 생성하던 포트폴리오 답변은 제공하지 않는다. 모든 사용자 표현을 키워드로 완벽히 분류할 수 없으므로, 인식하지 못한 요청에는 조건을 다시 안내하고 검증되지 않은 상품은 내보내지 않는다.

`recommendation_audits`에 요청 ID, 고객 ID, 정책 버전, 확인 시각, 판단에 사용한 성향·입출금 자산, 구조화 요청 조건, 후보별 위험등급·근거·제외 코드, 최종 상품·추천 근거가 저장된다. 개인정보 접근권한과 보관기간은 운영 환경에서 관리한다. 예외 로그에는 원문 자산/질의/DB 오류 내용을 출력하지 않는다.

## 검증과 평가

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r tests/suitability/requirements.txt
.\.venv\Scripts\python.exe -m pytest tests/suitability -q
```

테스트는 외부 LLM/DB IO를 대체하고 실제 정책·LangGraph·서비스·챗봇 응답을 실행한다. 위험·누락·비선호·무관상품·주입 시도·장애·빈 결과를 검사한다. 이 테스트 통과율을 실사용 부적합 추천률로 해석하지 않는다.

18% → 2%라는 수치는 이 변경에서 주장하지 않는다. 변경 전후 동일한 고객/질의/상품 스냅샷에 대한 실제 출력과 독립적으로 검토한 적합상품 정답을 수집한 후 `scripts/evaluate_suitability.py`로 비교한다. 부적합 상품 비율, 부적합 응답 비율, 추천 제공률을 함께 보고한다. 모두 빈 추천을 반환하는 시스템은 부적합률만으로 좋은 시스템으로 평가하지 않는다.

평가 입력은 JSONL이다. 정답 행은 `{"case_id":"case-1","allowed_product_ids":["상품ID"]}`, 변경 전/후 출력 행은 `{"case_id":"case-1","product_ids":["실제 반환한 상품ID"]}` 형식이다. 같은 case_id는 동일한 고객·질의·카탈로그 스냅샷을 의미해야 한다. 도구는 중복·누락 case_id와 중복 상품 ID를 거부한다. 출력이 모두 비어 상품 분모가 0이면 상품 부적합률을 `null`로 표시한다.

```powershell
python scripts/evaluate_suitability.py --labels labels.jsonl --before before.jsonl --after after.jsonl
```
