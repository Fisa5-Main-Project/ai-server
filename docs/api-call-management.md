# 대화·추천용 LLM API 호출 관리

## 구현 흐름

인증된 브라우저 → 기존 FastAPI 대화·추천 API → Spring 접근 JWT의 사용자 식별자 검증 → 공통 게이트웨이 → Redis 호출 허용 검사 → Gemini/Groq HTTP 호출 → MongoDB 사용량 기록 → 관리자 집계 API·화면.

`get_llm().ainvoke()`는 호출 관리 게이트웨이를 거치는 어댑터다. 현재 코드에서 대화·추천용 LLM을 호출하는 지점은 상품 추천 그래프다. 금융상품 적합성 규칙과 검증 결과를 바탕으로 최종 응답을 구성하는 방식은 유지했다. 챗봇 SSE의 청크 형식도 유지하되, 첫 청크를 준비한 다음 스트리밍 응답을 시작한다. 따라서 호출 제한이나 게이트웨이 장애를 헤더 전송 전에 실제 HTTP 429/503으로 반환할 수 있다. 공급자의 토큰 스트림을 중계하는 방식이 아니므로 일부 생성 내용을 전달한 뒤 재시도하는 경로는 없다.

## 호출 정책과 자원 관리

- **원자적 호출 허용 검사:** Redis Lua에서 최근 60초 동안의 전체·사용자별 호출량과 모델별 동시 실행 슬롯을 한 번에 검사하고 확보한다. Redis `TIME`을 사용해 서버 간 시계 차이를 피하고, 관련 키에는 동일한 Cluster 해시 태그를 적용했다. 거절된 요청은 전체·사용자별 RPM을 차감하지 않는다. 허용된 요청과 재시도는 각각 한도를 사용하며, 외부 처리 여부가 불확실한 실패는 사용한 한도를 되돌리지 않는다.
- **기본 한도:** 전체 분당 30회, 사용자별 분당 5회, 모델별 동시 실행 4개다. 운영 정책에 따라 변경할 수 있는 기본값이며, 특정 계정의 실제 계약 한도를 뜻하지 않는다. 사용자별 상한 안에서 남은 공용 한도를 활용한다. 과도한 호출을 제한하는 정책이며 사용자별 최소 처리량이나 엄격한 공정 스케줄링을 보장하지는 않는다.
- **재시도 제어:** 비동기 `httpx`로 직접 호출해 SDK 내부의 숨겨진 재시도를 제거하고 클라이언트·연결을 재사용한다. 명시적인 공급자 429만 최대 2회 시도한다. 초 단위 또는 HTTP 날짜 형식의 `Retry-After`를 존중하고 지수 백오프·지터와 서버 간 공용 대기 시간을 적용한다. 대기 시간이 남은 처리 시간을 초과하면 일찍 재시도하지 않고 429를 반환한다. 시간 초과·네트워크 오류·5xx는 실제 처리·과금 여부가 불확실하므로 자동 재시도하지 않는다.
- **동시 실행과 취소:** 슬롯 임대시간은 75초이며, 호출 허용 검사·사용량 저장·공급자 대기를 포함한 작업 제한시간은 60초다. 마지막 정리에는 슬롯 반환 2초와 기록 저장 3초의 별도 제한을 둔다. 정리 중 취소가 발생해도 이 절차를 수행한다. 정상 종료·오류·취소 시 슬롯을 반환하고, 첫 SSE 청크를 준비하는 동안에도 연결 종료를 감시한다. 프로세스가 종료되면 임대시간 만료로 슬롯을 회수한다. 단, 클라이언트 취소 후에도 외부 공급자의 작업은 계속될 수 있으므로 로컬 슬롯 반환이 외부 작업 종료를 보장하지는 않는다.
- **Redis 장애 정책:** Redis가 실패하면 외부 호출을 차단하고 503을 반환한다. 프로세스별 제한으로 우회해 계속 호출하지 않는다. 한도 데이터에는 LRU 캐시용 Redis 대신 영속화와 `noeviction` 정책을 적용한 전용 Redis를 사용하고, 배포 환경에 맞게 ACL·TLS·모니터링을 구성한다. Redis 장애 전환이나 AOF `everysec` 설정에서는 최근 허용 기록이 유실될 수 있다. 공급자 한도에 여유를 두며, 심각한 상태 유실 상황까지 정확한 과금이나 한도 초과 방지를 보장한다고 해석하지 않는다.
- **캐시와 토큰 제한:** 고객 프로필·제외 이력·상품 근거의 최신성을 유지하기 위해 최종 금융상품 추천 결과는 캐시하지 않는다. 입력 프롬프트 길이와 최대 생성 토큰 수는 제한한다. 분당 토큰 수(TPM), 일·월별 비용 상한을 강제하는 기능은 구현하지 않았다. RPM·동시 실행 제한과 토큰 계측은 별개의 기능이다.

## 인증 설정과 적용 절차

1. 변경된 `server/requirements.txt`의 의존성을 설치한다.
2. `.env.gateway.example`의 설정을 `server/.env`에 반영한다. Spring 서버와 **동일한 Base64 인코딩 HS512 접근 토큰 서명키**, **동일한 블랙리스트 Redis DB**를 설정한다. 서명 알고리즘을 고정하고 만료시간·사용자 식별자·권한 정보를 필수로 검증하며, 로그아웃 등으로 폐기된 토큰도 확인한다. 필수 인증 설정이 없으면 서버 시작에 실패하며, 개발용 무인증 우회는 제공하지 않는다.
3. 같은 공급자 한도를 공유하는 모든 서버는 동일한 `AI_LIMIT_POOL`과 Redis를 사용해야 한다. 풀을 나누면 각 풀이 별도로 한도를 허용한다. 모델별 동시 실행 제한은 설정된 모델에 적용하고, 전체 호출량 제한은 같은 풀·공급자 안의 모델들을 합산한다.
4. `docker-compose.gateway.yml`은 로컬 Compose 구성에 전용 호출 제한 Redis를 추가하는 오버레이 파일이다. 인증 Redis의 주소와 네트워크는 별도로 설정한다. 운영 네트워크는 환경에 맞춰 구성하며 Redis를 외부에 공개하지 않는다.
5. AI 서버를 재시작한다. `/health/llm`은 호출 제한용·인증용 Redis의 연결 상태를 확인하고, `/health/ready`는 기존 원천 데이터베이스 상태를 확인한다.
6. 기존 클라이언트는 접근 토큰을 전송한다. 요청 본문이나 경로의 사용자 ID는 JWT 사용자 식별자와 일치해야 하며, 다르면 403을 반환한다. 기존 관리자 API와 수동 벡터화 API에는 `ROLE_ADMIN`이 필요하다. 발급된 토큰의 권한 변경은 토큰 만료·폐기 이후 반영되므로, 이 경로에 Refresh Token을 사용하지 않는다.

관리자 화면은 `main-client`의 `/admin/ai-usage`다. 조회 API는 `GET /api/v1/admin/stats/llm-usage?days=7&user_id=7`이며, 기존 `/ai` 루트 경로로 배포하면 프록시 URL에 해당 접두사가 포함된다. `NEXT_PUBLIC_AI_BASE_URL`에는 기존과 같이 `/api/v1`까지 포함한다. 화면은 최근 1·7·30·90일 조회, 사용자 필터, 수동 새로고침을 지원하며 서버에서 관리자 권한을 검사한다. 주기적인 자동 조회나 LLM 호출은 수행하지 않는다.

## 사용량 집계 기준

- **호출 단위:** 기존 대화·메시지 통계와 별도로 `llm_usage`에 기록한다. 실제 호출 시도마다 고유한 `attempt_id`를 발급하며, 같은 시도의 완료 기록을 다시 저장해도 기존 행을 갱신하므로 중복 집계되지 않는다. `request_id`는 하나의 게이트웨이 요청에서 발생한 재시도를 연결한다. 프롬프트·금융 프로필·모델 답변·접근 토큰 원문·공급자 API Key는 사용량 기록에 저장하지 않는다.
- **상태와 장애:** 외부 호출 전에 `started`를 저장하고, 이후 `success`, `provider_429`, `rejected`, `timeout`, `failed`, `cancelled` 상태와 지연시간을 기록한다. 정상 호출은 두 번의 저장을 사용한다. 장애로 `started`가 남으면 `unfinished`로 확인해야 하며, 성공이나 비용 0으로 간주하지 않는다. HTTP 호출과 DB 저장은 분산 트랜잭션이 아니다. 성공 또는 429의 마지막 사용량 저장이 실패하면 계측 오류를 반환하며 공급자 호출을 재시도하지 않는다. 로그의 `attempt_id`로 기록을 대조할 수 있다.
- **토큰:** 공급자가 반환한 입력·출력·전체·캐시 입력 토큰 수를 저장한다. Gemini 출력 토큰에는 공급자가 보고한 추론 토큰도 포함한다. 메타데이터가 없으면 0으로 추정하지 않고 `null`로 유지한다. 집계에서는 확인된 합계와 함께 `unknown_usage_calls`, `unfinished`를 제공한다.
- **비용:** 운영자가 선택적으로 입력·출력 100만 토큰당 USD 단가를 설정하며, 사용한 단가를 기록에 남긴다. 단가가 없으면 비용을 추정하지 않는다. 캐시 입력 할인·구간별 요금 등 세부 과금 정책을 정산하지 않으므로 단순 추정치이며 실제 청구액은 아니다. 화면에는 토큰 사용량이 확인되지 않은 호출 수도 표시한다.
- **조회와 보관:** 서버에서 집계하며 조회 범위는 최대 90일, 집계 실행 제한은 `maxTimeMS=5000`이다. 사용자·기능·모델별 그룹을 최대 500개 반환하고 잘림 여부를 표시한다. TTL을 통한 기본 보관기간은 90일이며, 만료된 기록의 실제 삭제 시점은 MongoDB TTL 작업 주기에 따른다.
- **적용 범위:** 기존 검색·ETL·CDC 임베딩은 원래 클라이언트를 사용하므로 이번 **대화·추천 생성용** 사용량 기록과 호출 제한의 범위 밖이다. 수동 벡터화는 관리자만 실행할 수 있다. 임베딩 모델과 같은 공급자 한도를 공유한다면 별도 인증키·할당량을 사용하거나 임베딩용 어댑터를 추가해야 전체 호출을 제어할 수 있다. 같은 비밀키로 외부 서비스를 직접 호출하는 요청은 게이트웨이의 사용자별 사용량으로 식별할 수 없다.

## 검증 명령

프로젝트 가상환경에 `tests/gateway/requirements.txt`의 의존성을 설치한 뒤 실행한다. 테스트에서는 유료 LLM API를 호출하지 않는다.

```powershell
$env:TEST_REDIS_URL='redis://127.0.0.1:16389/0'
$env:TEST_MONGO_URL='mongodb://127.0.0.1:27029'
.venv/Scripts/python.exe -m pytest tests/gateway -q
```

위 환경변수가 없으면 실제 Redis·MongoDB 통합 테스트는 건너뛰고, `fakeredis`에서 실제 Lua 스크립트를 실행한다. 통합 테스트는 고유한 Redis 키 그룹과 MongoDB 테스트 데이터베이스를 사용하며 공유 데이터베이스 전체를 비우지 않는다. Docker 테스트 컨테이너는 로컬 루프백 전용 포트를 사용하고 검증 후 정리한다.
