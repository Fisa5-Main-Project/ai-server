# 상품 근거 보강과 내부 위험분류

## 이번 변경의 전제

수집 상품에 위험등급이 존재하지 않는다. 따라서 존재하지 않는 공식 등급을 생성하지 않는다.
`official_risk_grade`는 미확인 상태인 `null`로 유지하고, 확인된 사실로부터 별도의 `risk_assessment`를 계산한다.

- 일반 원화 예금 구조와 해당 상품의 예금자보호 대상 여부가 함께 확인됨: **내부 위험분류 낮음**.
- 확인된 레버리지·파생·구조화·주식형·벤처 투자 구조: **내부 위험분류 높음**.
- 그 외, 또는 구조를 판단할 근거 부족: **미확인**, 추천 제외.

비교용 숫자 6/2는 기존 정책 엔진과 연결하기 위한 내부 값이다. 발행사나 금융감독원의 공식 투자위험등급이 아니다. 상품명에 '안전', '채권', 'MMF'가 있다는 이유로 낮은 위험을 부여하지 않는다. 현재 공식 자료를 확보한 것은 아래 예금 3종이며, 다른 상품은 미확인으로 남는다.

예금자보호와 무제한 원금보장은 다르므로 `deposit_protected=true`를 `principal_guaranteed=true`로 변환하지 않는다. 따라서 별도 원금보장 근거가 필요한 기존 원금보장형 정책을 자동 우회하지 않는다. 위험분류와 가입 가능 여부도 독립적이다.

## 연결 방식

근거 파일: `server/app/rag/data/product_evidence.json`.

각 필드는 `value`, `source_id`, `locator`를 갖는다. 출처에는 발행기관, 공식 URL, 문서기준일을 저장하고, 자료를 확인한 날짜는 `checked_on`으로 따로 기록한다.

상품군 + 금융사 + 상품명을 일치시켜 연결한다. 공백·대소문자만 정규화하며, 특판/클래스 등 다른 이름에 유사매칭하지 않는다. 금융사 명칭 차이는 명시한 별칭만 허용한다.

검색 결과에 메타데이터가 없거나 새 스키마(v2)이면 반환 전에 근거를 적용한다. 운영 서버 컨테이너에 JSON이 앱 코드와 함께 포함된다. DB를 미리 갱신하지 않아도 일치하는 상품은 조회 시 보강된다. 기존 수동 v1 메타데이터는 호환성을 위해 유지하며, 전체 카탈로그를 새 근거 체계로 전환하려면 backfill을 적용해야 한다.

아래 상태에서는 내부 위험도를 부여하지 않는다.

- `unmatched`: 일치하는 근거 없음
- `ambiguous`: 동일 상품에 여러 근거 레코드 매칭
- `stale`: 확인일이 미래이거나 30일을 초과
- `conflict`: 원천 가입제한과 근거가 충돌하거나 종료일 형식 오류
- `closed`: 공시 종료일 도래

반복 조회나 배치 재실행은 `checked_on`을 오늘로 바꾸지 않는다. 원천 필드와 근거 식별자·내부 정책 버전·해시를 기록해 판단을 추적할 수 있다. 해시는 원천 스냅샷 식별용이며, 원격 공식 페이지의 내용이 바뀌었는지를 자동 감시하는 기능은 아니다.

## 기존 데이터 일괄 보강

원본 JSON 배열을 다른 파일로 변환:

```powershell
.\.venv\Scripts\python.exe scripts/enrich_product_evidence.py --input products.json --output products.enriched.json
```

MongoDB는 기본적으로 쓰지 않고 상태별 건수만 확인한다. 설정 파일에는 `MONGO_URI`, `MONGO_DB_NAME`이 필요하다. 키나 비밀번호를 명령 인수로 넣지 않는다.

```powershell
.\.venv\Scripts\python.exe scripts/enrich_product_evidence.py --mongo --env-file server/.env
.\.venv\Scripts\python.exe scripts/enrich_product_evidence.py --mongo --env-file server/.env --apply
```

대상 컬렉션은 `products_deposit_saving`, `products_annuity`, `products_funds`다. 임베딩과 상품 본문은 유지하고 `suitability`만 갱신한다. 읽은 뒤 원천 데이터가 바뀌면 해당 행은 쓰지 않고 `concurrent_change`로 집계한다. 일치하는 근거가 없는 상품의 기존 분류도 미확인으로 전환하므로, dry-run의 보류 건수를 확인해야 한다.

## 검증 및 적용 상태

테스트는 실제 분류·매칭·정책·출력과 MongoDB 대역을 이용한 backfill을 실행한다. 공식 페이지를 자동 재수집하거나 전체 운영 상품의 근거를 수집한 것은 아니다.

이 작업 환경에는 실제 상품 내보내기 파일, MongoDB 연결 설정, 금융 API 키가 없어 **운영 DB 갱신은 실행하지 않았다**. 실제 목록에 대한 보강 건수·매칭률도 아직 산출하지 않았다. 연결 설정 또는 상품 파일이 제공되면 같은 도구로 적용할 수 있다.
